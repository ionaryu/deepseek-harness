# Agent Note: 라우트의 모델 탐색을 자체 엔드포인트로 옵트인

Status: implemented

[English](2026-09-10-pi-ai-discover-from-endpoint.md) | 中文

## 문제

「사용 가능한 모델 가져오기」는 이름이 지정된 라우트를 네트워크 호출 없이 설치된 pi-ai 카탈로그로 답합니다. 이것이 올바른 기본값입니다 — pi-ai 레지스트리는 자체 프로바이더에 대해 권위를 갖고, 목록 엔드포인트가 알려 주지 않는 컨텍스트 윈도우와 출력 캡을 함께 실어 주기 때문입니다. 그러나 동시에 스냅샷이기도 합니다: 설치된 pi-ai 릴리스 이후 프로바이더가 추가한 모델은 Models 페이지에 절대 나타나지 않습니다. 실제 사례: `opencode-go` 라우트는 설치 엔트리 27개를 배송하지만 실제 목록인 `https://opencode.ai/zen/go/v1/models`는 36개 모델을 광고하며, 문서화된 우회법 — 같은 게이트웨이를 커스텀 프로바이더로 재선언해 discovery의 네트워크 경로에 도달 — 는 실제 서비스 목록을 보려고 하나의 라우트를 두 키로 복제하게 만듭니다.

## 결정

라우트는 `discoverFromEndpoint: true`를 설정할 수 있습니다. 이 라우트의 탐색은 설치 카탈로그 답변을 건너뛰고 엔드포인트를 대신 묻습니다: 폼이 보여 주는 초안의 `baseURL`, 초안이 비워 두면 라우트가 선언한 `baseURL`, 그리고 어느 것도 없는 카탈로그 기본 저장 라우트라면 이 라우트의 목록 조회 프로토콜을 말하는 설치 모델들이 도달하는 엔드포인트입니다. 응답은 같은 id의 설치 엔트리로 보강됩니다: 카탈로그가 여전히 설명하는 목록 id는 그 엔트리의 컨텍스트 윈도우·출력 캡·(목록에 없을 때) 표시명을 상속합니다. 카탈로그가 설명하지 않는 목록 id는 설치 기본값으로 구체화될 수 없으므로, 탐색 자체가 사용한 프로토콜과 엔드포인트를 실어 옵니다 — 채택된 행은 항목 단위로 선언합니다(`models` 항목의 `api`와 `baseURL`, 라우트 자신의 것보다 우선) — 그리고 목록이 공개하지 않는 부분은 라우트의 용량 기본값으로 서비스됩니다. 카탈로그에만 있는 id는 절대 추가되지 않습니다 — 존재 여부는 엔드포인트가 결정하며, 그것이 물어보는 이유입니다. 탐색은 아무것도 저장하지 않고, 옵트인하지 않은 모든 라우트는 카탈로그 답변을 그대로 유지합니다.

## 고려된 대안

**모든 named 라우트를 엔드포인트로 묻기.** 기본값을 뒤집으면 모든 내장 프로바이더의 fetch가 네트워크 호출이 되고, 목록이 레지스트리보다 적게 공개하는 프로바이더의 응답 품질이 떨어집니다. 레지스트리가 완전한 곳에서 더 나은 답이며, 뒤처진 카탈로그만 회선이 필요하므로 기각.

**커스텀 프로바이더 우회법 유지.** pi-ai가 제공하지 않는 라우트 키로 게이트웨이를 재선언하면 오늘도 네트워크 경로에 도달합니다. 제품 답변으로는 기각: 라우트가 복제되고 하나의 프로바이더 정체성이 두 키로 갈라지며, 원인이 사용자에게서 숨겨집니다.

**보강 없는 엔드포인트 응답.** 모든 목록 행은 목록이 공개하는 것만 실어 옵니다. opencode-go처럼 (id만 있는) 목록에서는 어떤 모델을 채택하더라도 설치 카탈로그나 탐색이 이미 기록한 와이어 사실과 용량을 손으로 입력해야 합니다. 행이 부분적으로만 공개하는 것은 레지스트리가 더 나은 출처이므로 기각.

**opencode 라우트를 위한 provider-id 규칙.** `opencode*` 키를 특수 취급하면 한 프로바이더의 엔드포인트 관례가 어댑터에 굳어집니다. 뒤처진 카탈로그 상황은 일반적이므로 선택은 라우트 설정에 속한다 — 기각.

## 결과

Models 페이지는 재선언 없이 프로바이더의 실시간 카탈로그를 드러낼 수 있고, 채택된 행은 카탈로그가 id를 설명하는 곳에서 실제 용량을 유지하며, 모르는 id는 자체 와이어 선언을 실어 사용자가 채울 때까지 라우트의 `defaultContextWindow`/`defaultMaxTokens`로 동작합니다. 옵트인 라우트의 fetch는 네트워크 호출 한 번을 소모하고 엔드포인트 실패를 discovery 오류로 보고합니다 — 그것이 물어보는 이유입니다. 하나의 설정 필드, 두 개의 항목별 필드, 그 JSDoc이 생성된 구성 카탈로그에 합류하며, 저장 형식·와이어 형태·세션 이벤트는 바뀌지 않습니다.

## 테스트

discovery 스펙은 로컬 목록 서버로 옵트인 탐색(엔드포인트 URL, 저장 자격 증명 bearer, 용량 보강, 완성된 행의 원형 유지, 탐색의 프로토콜과 엔드포인트를 실은 설명되지 않은 행), baseURL을 선언하지 않는 저장 라우트의 카탈로그 유도 엔드포인트(`https://opencode.ai/zen/go/v1/models`, fetch 스텁), 카탈로그 라우트의 누락 프로토콜 패밀리 거절, 변하지 않는 기본 카탈로그 답변을 고정합니다. config 스펙은 플래그의 명시적 해석을, catalog 스펙은 설명되는 id와 설명되지 않는 id의 항목 단위 와이어 선언을, LLM 런타임 스펙은 정규화된 행을, provider-form 스펙은 채택된 행의 기록을 고정합니다.
