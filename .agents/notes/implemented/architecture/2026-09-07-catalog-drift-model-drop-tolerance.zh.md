# Agent Note: Dropping stored models the catalog no longer describes

Status: implemented

[English](2026-09-07-catalog-drift-model-drop-tolerance.md) | 中文

## 问题

`llm-pi-ai` 设置命名空间下存储的 `providers.<route>.models` 列表是针对当时 pi-ai 目录拍摄的快照。当已安装目录在 pi-ai 版本之间变化——真实案例：opencode-go 目录从 0.84.2 的 19 个模型（含 `grok-4.5`）变为 0.84.4 的 25 个，移除了 `grok-4.5`、加入了 `glm-5.3-flash`——一份此前有效的存储列表会变得无法服务。`resolveRouteModels` 会对已安装目录不再描述的第一个条目抛出异常（`model "X" needs an api` 或 `needs a baseURL`；已安装目录不描述它），于是 `resolveProfiles`、进而 settings 命名空间校验器 `assertServiceable`，都会把错误继续向上传播。

失败在最糟的位置浮出水面。settings seam 注册每个命名空间时，会先经所有者的校验器解析已存储分节；此时还没有"最后有效值"，存储分节解析失败会直接拒绝注册本身。因此整个 `dsh-llm-pi-ai` 插件在启动时无法激活：Web Models 页面丢失了全部 pi-ai 提供方行（只剩 deepseek-official 系列），添加控件也停止工作。一个过期的模型 id 就禁用了整个提供方家族，而且每次 pi-ai 目录变化都会复发。

## 决策

一个只因已安装目录不再描述它而无法实体化的存储模型条目，不再让其路由失败。该原因既狭窄又具有结构性：路由目录当前至少提供 1 个模型，条目不在其中，路由既未设置 `api` 也未设置 `baseURL`（存储快照从未碰过它们），且路由级回退（`routeApi`、提供方 `baseUrl`）同样无法补足协议格式或端点。`resolveRouteModels` 会把这类条目记录到返回的 `RouteCatalog.dropped`（各带 id 与原因），并继续服务其余所有模型，这与 `discovery.ts` 的 `readListing` 跳过无法使用的列表行而非让整个询问失败的做法一致。跳过绝不静默：解析后的 profile 携带 `droppedModels`，`dsh-llm-pi-ai` 的 apply 每次配置变化记录一条警告，点名提供方、被丢弃的 id 与补救办法（"在 Models 页重新获取模型或升级 pi-ai"）。存储的 `settings.yaml` 行保持原样——不会从磁盘删除任何内容——因此未来 pi-ai 版本再次描述该 id 时，它会在下一次解析自动回归。

其余所有拒绝原封不动。空 id、重复 id、落空的 `modelOverrides`（包括点名目录未描述的模型）、与 `models` 列表并存的 `modelOverrides`、空的 `defaultInput`、无效的标头与容量、协议不接受的内核兼容字段、以及 reasoning-efforts 错误，全部照旧抛出。配置列表把**每个**条目都丢弃的路由仍然拒绝，并点名过期 id：没有任何模型可服务的路由是配置错误，绝不是一条静默的空路由。丢弃路径同样对目录完全不提供的路由关闭——说明不完整的手工声明条目保留原有的 `needs an api` / `needs a baseURL` 拒绝，因为这里没有可供过期的快照。

写入点名同一原因时如今也被容忍。settings seam 对加载（注册与外部发布）和写入（`update` / `replace` / `mutate`）运行同一个校验器，解析也经过这同一个钩子，因此在当前 seam 内、不改动 `dsh-settings` 的前提下，容忍加载的校验器无法同时拒绝写入。仅针对这一原因的统一容忍被接受，并在 `assertServiceable` 的 JSDoc 中记录。暴露面有限：Models UI 只采纳发现结果，而这些结果始终可被已安装目录描述，因此通过页面够不到目录路由上的真实拼写错误；手工声明路由携带 `api` 与 `baseURL`，其条目按构造即可描述；`modelOverrides` 仍是硬拒绝。

## 考虑过的替代方案

**继续拒绝并让注册失败。** 现状让插件在每次 pi-ai 目录变化时于启动阶段死亡——这就是事故本身。拒绝采用，因为本变更正是为消除该失败而存在。

**改写存储分节。** 加载时从 `settings.yaml` 修剪过期 id，或不容忍并强制重新获取。两者都会未经同意删除或修改用户数据，还会与文件监视器及修订计数打架；当后续目录再次描述被移除的 id 时，两者都无法让它回归。拒绝——存储行绝不改动。

**加载容忍、写入严格。** 首选拆分：读取已存储分节时容忍漂移原因，调用方写入相同内容时继续拒绝。在当前 settings seam 内做不到，因为 `register`、`publish` 与写入路径都经同一个 `validate` 钩子解析，拆分意味着为一个消费者的原因改动 `dsh-settings`。因范围而拒绝；该权衡记录于此与 JSDoc 中。

**静默丢弃。** 不记日志、不带 `droppedModels` 记录地继续服务其余模型。拒绝——操作者看不到的丢弃会让它取代的"静默禁用"以更小规模复活。全部丢弃时的拒绝还保证了"过期快照"不会悄悄变成"什么都不服务"。

**在任何路由上容忍该原因。** 无论路由目录是否仍提供模型都丢弃未描述条目。pi-ai 不提供的路由上，说明不完整的条目是正在被写入的配置错误，而非过期快照；正是其拒绝消息告诉作者补上 `api`/`baseURL`。拒绝——把丢弃限制在目录仍提供模型的路由上，可以保留该诊断以及钉住它的手工声明路由测试。

## 后果

当存储分节点名已安装目录不再描述的 id 时，插件仍能挂载并继续服务：启动不再死亡，Models 页面保留该提供方的其余行与可用的添加控件，一条警告点名被丢弃的内容及恢复方式。设置文档不被改动，因此采纳更新的目录（或回退 pi-ai）会在下一次解析时无需任何编辑就恢复被丢弃的 id。

容忍写入的权衡是唯一的行为放宽。点名过期模型 id 的设置写入会被存储而非拒绝（此前的行为），因为 seam 无法分别裁决加载与写入；此前的推理——Models UI 只能写入发现返回的内容，而发现返回的总是目录可描述的模型——限定了暴露面。其余所有拒绝，包括全部丢弃的路由，行为与先前一致。由于丢弃在带记忆的 profile 解析内部每次配置变化只记录一次，适配器快照依赖的记忆标识不受影响：注册事实与目录事实仍取自每个 profile 的同一子集。

## 测试

包测试套件用目录漂移用例钉住语义：一个过期 id 加一个活模型的存储列表只服务活模型并上报被丢弃的 id；每个条目都过期的列表会拒绝并点名 id；为未描述 id 声明了传输的路由仍拒绝其缺失的协议；带过期 id 的存储文档能让插件启动、服务存活模型并只记一次丢弃日志；点名过期 id 的设置写入会被接受且存储行保持原样。此前把 `xai` 混合协议目录钉死的两个既有用例现在改为选择满足其前提的任意已安装路由，因此目录变动不会再破坏它们。完整 `dsh-llm-pi-ai` 套件在已安装 pi-ai 版本上全部通过。
